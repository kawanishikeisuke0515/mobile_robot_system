# 3軸クローズドループ速度制御 仕様書

版：0.4 ／ 作成日：2026-09-28 ／ 状態：検討用ドラフト

## 1. 目的と範囲

`locomotion_core` とは別の `mobile_robot_system/src/locomotion_closed_loop/` に、ZED_WRAPPERからの実測速度を使う車体速度制御を構築する。前後・左右・旋回の3軸を対象とする。

本書は仕様のたたき台。v0.4で初期実装を追加した。既存locomotion_coreは変更せず、別パッケージとして提供する。以下の案・未決定事項に対する暫定実装値と未実装範囲は第14節に記載する。

## 2. 合意済みの前提

- 制御対象は前後 `vx`、左右 `vy`、旋回 `wz` の3軸すべて。
- 初期実装はP制御のみとする。I項・D項は実装しない。
- 目標速度入力は既存の `/rov_cmd_vel`（`geometry_msgs/msg/Twist`）を想定する。会話中の `rov_vel_cmd` に対し、コード上の名称は `/rov_cmd_vel`。
- `linear.x` と `linear.y` は m/s、`angular.z` は rad/s。
- フィードバックにはZED_WRAPPERの速度を使用し、移動平均フィルタを掛けて使えるようにする。
- 既存の `×1000`（並進）と `×30`（旋回）は調整用ゲインとして扱う。単位変換という説明は採用しない。
- 現行の固定出力制限 `±15` を外す方針とする。ドライバーの許容範囲に基づく最終出力上限は別途決定する。

## 3. 現行実装の確認結果

確認元：`locomotion_core/locomotion_core/rover_velocity.py`、`RoverDescription.py`、`cmd_roboteq.py`。

| 処理 | 現行の動作 | 新仕様での扱い |
| --- | --- | --- |
| 目標入力 | `/rov_cmd_vel` のTwistを購読 | 同じ入力形式を使用する案 |
| 入力ゲイン | `[1000 × vx, 1000 × vy, 30 × wz]` | 調整用ゲイン。パラメーター化する案 |
| 各輪への配分 | `kinematic_equation()` を使用 | 軸、符号、車輪順を照合して定義 |
| 固定制限 | 各輪を個別に `[-15, 15]` に制限 | 新実装では引き継がない |
| 出力 | `rov/motors`、Float32MultiArray、4要素 | 既存ドライバーとの接続候補 |
| 送信周期 | 0.1秒 | 新制御周期はZED更新周期とともに決定 |
| ドライバー | 値を整数化・符号反転し、`!G` で送信 | 指令単位と実機モードを要確認 |

変数名は `rpm_vec` だが、この経路では `vel_to_rpm()` は呼ばれていない。本書では `/rov/motors` の値を「モーター指令値」と呼び、物理量としてのRPMとは断定しない。

配列の要素0・1は前側ドライバーのチャンネル1・2、要素2・3は後側ドライバーのチャンネル1・2に送信される。各チャンネルと実際の車輪位置・正回転方向の対応は実機確認事項とする。

## 4. 構成案

```text
ZED_WRAPPER → odom → 入力検証 → 車体座標・基準点へ変換
                                  ↓
                          3軸の移動平均フィルタ
                                  ↓
/rov_cmd_vel → 目標速度 ──→ 目標速度 − 平滑化した実測速度
                  │               ↓
                  └──────→ 目標速度 ＋ 軸別P補正
                                  ↓
                          出力ゲイン → 4輪配分
                                  ↓
                          最終出力制限 → ドライバー → ロボット
```

入力の鮮度と有効性はフィルタとは独立に判定し、異常時は制御出力をゼロにする。

新ノードの仮称は `closed_loop_velocity`。既存の `rover_velocity` と新ノードが同時に同一モータートピックへ出力しない起動構成にする。

## 5. 入出力案

| 種別 | トピック | メッセージ | 用途 |
| --- | --- | --- | --- |
| 入力 | `/rov_cmd_vel` | `geometry_msgs/msg/Twist` | 目標vx・vy・wz |
| 入力 | `/zed2i/zed_node/odom` | `nav_msgs/msg/Odometry` | `twist.twist.linear.x/y`、`angular.z`を含む実測速度 |
| 出力 | `/rov/motors` | `std_msgs/msg/Float32MultiArray` | 4輪のモーター指令値 |
| 接続検討 | `/deadman` | `std_msgs/msg/Bool` | 既存ドライバーの有効化との整合。発行主体は未決定 |
| 診断 | 名称・型は未決定 | 未決定 | 目標、フィルタ前後の実測、誤差、出力、飽和、停止理由 |

トピック名はパラメーターまたはremapで変更できる構成を想定する。ZEDトピック名は既存のdata hub仕様書に基づく候補であり、実機の型・更新周期・QoS・速度フィールドの配信状況を確認する。

## 6. 実測速度の座標系

比較する目標速度と実測速度は、車体基準の同じ座標系・同じ基準点にそろえる。車体軸は前方を+x、左方を+y、上方を+zとする案。正のwzは上から見た反時計回りとする。

ZED odomの `child_frame_id` と、速度が表す基準点を実機で確認する。カメラ基準の速度である場合は、軸の回転変換だけでなく、車体中心からカメラまでの取付位置も考慮する。すでに車体基準に変換された速度を二重に補正しない。

車体中心からカメラ基準点へのベクトルを車体座標で `r` とすると、剛体の関係は次の通り。

```text
v_body_origin = R × v_camera − omega_body × r
omega_body   = R × omega_camera
```

変換後のvx・vy・wzに移動平均フィルタを適用し、その結果を制御に使用する。必要なTFが得られない場合の扱い、固定取付値を設定として持つかは実装前に決める。

## 6.1. ZED速度の移動平均フィルタ案

車体座標・基準点への変換後に、vx・vy・wzの各軸へ単純移動平均を適用する。3軸で同じサンプル群と共通の窓サイズNを使用し、軸ごとに算術平均を計算する。目標速度にはこのフィルタを掛けない。

```text
q_body[k] = 車体座標・基準点に変換した最新の有効な実測速度
m         = min(N, リセット後に受け入れたサンプル数)
q_filtered[k] = (q_body[k] + ... + q_body[k-m+1]) / m
q_meas    = q_filtered[k]
```

- `velocity_filter_enabled` で有効・無効を切り替える。無効時は最新の有効なq_bodyを使用する。
- `velocity_filter_window_size` は1以上の整数。N=1は平滑化なしと同じ。N=0、負数、小数は設定エラーとして受け付けない。
- 新しい有効なodomサンプルを受け入れたときだけ履歴を更新する。制御タイマーごとに同じサンプルを重複追加しない。同一ヘッダー時刻の再配信も追加しない。
- 初期状態とリセット直後は、到着済みのm個で平均する。ゼロ埋めせず、N個がそろうまで待たない。1個もない間は速度未受信としてゼロ出力とする。
- 制御周期では最新の平均値を参照するが、鮮度は元のodomの受信時刻・計測時刻で判定する。平均値を再利用しても鮮度を更新しない。
- ZED更新途絶、無効値（NaN/Infを含む）、必要な座標変換不可、検出された追跡異常、計測時刻の逆行・時刻リセットでは、3軸すべての履歴を破棄してゼロ出力とする。古い履歴で異常を隠さない。復旧後は新しい有効サンプルから平均を再開する。駆動の復帰条件は第9節で別途定める。
- 停止指令や目標指令の途絶だけでは、有効なZEDの履歴を破棄しない。ゼロ出力中も観測を続ける。
- 設定は起動時に読み込む案とする。動作中の窓サイズ変更は初期実装の対象外とする。

窓サイズを大きくすると速度の細かな揺れを抑えられる一方、応答が遅くなる。等間隔のサンプル周期をTとすると、窓が満ちた移動平均の遅延の目安は `(N−1)×T/2`。例えば30 Hz・N=5なら約67 msであり、ZED自体や通信の遅延は別に加わる。これは説明用の例で、実機の配信周期や採用値を示すものではない。

本方式はサンプル数による窓であり、時間幅固定の平均ではない。到着間隔が変動すると履歴の時間幅も変わるため、使用サンプル数と最古・最新の計測時刻の差を診断に記録する。有効を初期設定とする案とし、Nの初期値はノイズ・遅延・追従性を比較して決める。

## 7. 制御則案

3軸を独立したP制御で補正する。目標速度を基本入力として加え、速度誤差に比例する補正を上乗せする。I項・D項は使用しない。横移動・前後移動・旋回でゲインを別々に設定する。

```text
q_target = [vx_target, vy_target, wz_target]
q_meas   = [vx_filtered, vy_filtered, wz_filtered]  # フィルタ無効時は最新の車体基準実測値
e        = q_target − q_meas
q_ctrl   = q_target + Kp ⊙ e
u_raw    = M × (G ⊙ q_ctrl)
```

`⊙` は軸ごとの積、`M` は4輪への配分行列、`G` はモーター出力を調整する軸別ゲイン。P補正は並進m/s・旋回rad/sの段階で行い、出力ゲインとは分離する。`Kp` は無次元。`G` と `M` を通した結果の指令単位はドライバー仕様を確認して定義する。

現行の1000・1000・30は比較用の既存値として記録し、新しい閉ループ制御の確定ゲインとはしない。制御周期、ゲイン、移動平均の窓サイズは計測後に決定する。今回の実装にはKi、積分状態、積分上限、アンチワインドアップ処理を設けない。P制御で残る定常誤差は評価結果として記録する。

## 8. 固定±15制限の撤廃と最終出力

撤廃対象は `rover_velocity.py` にある各輪の固定 `±15` 制限。新実装ではこの制限を引き継がない。既存ノード自体も変更するかは実装範囲として別途決める。

ドライバー指令の許容範囲を確認したうえで、最終出力上限をパラメーターにする案。共通上限を `Umax` とすると、上限超過時は次の比率で4輪を一括縮小する。

```text
scale = min(1, Umax / max(abs(u_raw)))  # 全要素ゼロならscale=1
u_out = scale × u_raw
```

一括縮小は配分した4輪の比率を維持するための処理であり、実機の速度方向を保証するものではない。飽和状態と制限前後の出力を記録し、上限によって目標速度への追従が制約されていることを確認できるようにする。

## 9. 動作状態と停止案

| 状態・条件 | 出力の扱い |
| --- | --- |
| 起動直後、入力未受信 | ゼロ出力 |
| 有効な目標・実測がそろう | 3軸制御を実行 |
| 3軸すべてがゼロの停止指令 | ゼロ出力 |
| 1軸だけ目標ゼロ | 他軸とともにP制御を継続。その軸の実測速度もゼロへ追従 |
| 目標指令の更新途絶 | ゼロ出力 |
| ZED更新途絶・無効値・必要な座標変換不可 | ゼロ出力 |
| 追跡異常 | 有効性判定の情報源を確定後、停止条件として実装 |

全軸ゼロ時は、積極的に速度ゼロへフィードバックする保持制御ではなく、モーター指令ゼロを出す案。これは機械的な即時停止や位置保持を意味しない。復帰時に新しい目標指令を要求するか、自動復帰するかは未決定。

Twistには時刻がないため目標指令の鮮度は受信時刻で判定する案。ZEDは受信時刻とヘッダー時刻の双方を確認し、同じ古いデータの再配信を新鮮な計測として扱わない。タイムアウト値、許容遅延、時刻不連続時の扱いを定義する。

既存ドライバーのコードには受信途絶を監視して停止する処理が見当たらない。新制御ノードが停止した場合はゼロ出力を送れないため、ドライバー側または機器側のウォッチドッグを確認する。`deadman=False` は次のモーター指令コールバックで反映される実装であり、Boolを送るだけで即座に停止する仕様とは扱わない。

## 11. 確認・評価の進め方

1. ZEDの静止・前後・左右・旋回時の速度を記録し、単位、符号、座標系、更新周期、遅延を確認する。
2. ドライバーの運転モード、`!G` の指令単位・範囲、車輪順、符号、整数化の影響を確認する。
3. 新実装で固定±15制限を除いた出力経路を確認する。初期ゲインは実測に基づいて決める。
4. フィルタ無効・N=1・複数の窓サイズで、静止時の揺れと速度変化時の遅延を比較する。選んだ窓サイズでKpを各軸個別に調整し、その後に3軸同時入力を評価する。
5. P制御で残る定常誤差、振動の有無、飽和からの復帰を確認する。
6. フィルタの初期サンプル、同一データの重複排除、異常時の履歴破棄、復旧後の再開を確認する。
7. 停止指令、目標更新途絶、ZED更新途絶、無効値、制御ノード終了時の停止経路を確認する。

記録項目は時刻、目標速度、車体基準のフィルタ前後の実測速度、フィルタ設定、使用サンプル数、履歴の時間幅、誤差、P補正、制限前後の4輪出力、飽和状態、計測の経過時間、動作状態と停止理由。追従誤差、整定時間、オーバーシュート、停止までの時間の合格値は未決定。

`locomotion_closed_loop` のROS 2 Pythonパッケージを実装した。起動手順は [README](../README.md) を参照。

| 項目 | 初期実装 |
| --- | --- |

| 周期 | 暫定30 Hz |

| 設定変更 | 起動時のみ。実行中の変更は拒否 |
| 診断 | 専用トピックへJSON形式でフィルタ前後、制御量、状態を配信 |

これらの数値は実機チューニング済みの値ではない。モーター指令上限は未確定のため、実機で確認した正の上限を設定するまで駆動しない。

追跡状態トピックの購読・品質異常判定は未実装。odom鮮度・非有限値・時刻逆行・TF取得失敗を検出する。ドライバー側ウォッチドッグとdeadman発行は実装範囲に含めていない。制御ノード終了時のゼロ送信はROSコンテキストが有効な場合のベストエフォートであり、通信断や強制終了への停止保証は実機側・ドライバー側で対応する。
